## 1. What it is
84 DESIGN.md files, each a plain-markdown "design system" reverse-engineered from a real brand's public website (Stripe, Linear, Nike, Airbnb, Bugatti, WIRED…, plus a "Retro Web" series: Dell 1996, Nintendo 2001). Idea: drop one into a project root and tell the coding agent "build a page that looks like this". Format follows Google Stitch's DESIGN.md spec with extra sections. Maintained by VoltAgent; also feeds a commercial site (getdesign.md, paid/private requests).

Files read for this sheet (8 across styles): wired (editorial), bugatti (luxury), nike (bold retail), airbnb (warm consumer), linear.app (dark dev tool), dell-1996 (brutal/retro catalog), nintendo-2001 (playful Y2K), kraken (old format). README + CONTRIBUTING read in full.

## 2. How it works
- One folder per brand: `DESIGN.md` + a stub README pointing to getdesign.md. The README says each brand also ships `preview.html` / `preview-dark.html` (swatch/type/button catalog) — these are NOT in the clone at this commit.
- Two formats coexist (grouped by section headings across all 84):
  - Old (10 files, e.g. kraken): 9 numbered sections — 1 Visual Theme & Atmosphere, 2 Color Palette & Roles, 3 Typography Rules, 4 Component Stylings, 5 Layout Principles, 6 Depth & Elevation, 7 Do's and Don'ts, 8 Responsive Behavior, 9 Agent Prompt Guide (quick colour list + ready-made prompts like "Create hero: white bg, 48px/700, -1px tracking, purple CTA 12px radius").
  - New (74 files): YAML front matter with tokens (`colors`, `typography` with size/weight/line-height/tracking per role, `rounded`, `spacing`, `components` that reference tokens as `{colors.ink}`), then prose: Overview (+ Key Characteristics), Colors (Brand/Surface/Text/Semantic), Typography (families, hierarchy table, principles, open-source substitutes), Layout (spacing, grid, whitespace philosophy), Elevation & Depth (level table), Shapes (radius scale + photo geometry), Components (each named, with tokens), Do's and Don'ts, Responsive Behavior (breakpoint table, touch targets, collapsing strategy, image behaviour), Iteration Guide, Known Gaps.
- Generated by tooling: mentions a "dembrandt" colour-frequency analyser, screenshots, a `derive-examples-block.mjs` script that auto-adds 10 generic `ex-*` components (pricing tier, modal, toast…), with `TO_FILL` markers left in 13 files. Iteration Guides tell agents to run `npx @google/design.md lint` (broken refs, contrast, orphaned tokens) — not run here.
- House policy in ~20 files: "Never document hover. Default and Active/Pressed states only" (hover extraction judged unreliable).

## 3. Rules
What makes a good DESIGN.md (the reusable lessons, brand-neutral):
- [process] Write a one-paragraph "Overview" that states the design's single governing idea before any token (e.g. "photography speaks, chrome doesn't"; "printed magazine ported to the web"; "console hardware").
- [process] Follow the overview with 5–7 "Key Characteristics" bullets — the identifiers that make it recognisable; these are what an agent must not lose.
- [process] Every token gets a semantic name AND a job ("Body #757575: bylines, timestamps"), never a bare hex list.
- [process] Store tokens once (front matter) and reference them everywhere by name; never inline hex in component specs.
- [process] End with explicit Do / Don't lists phrased as hard limits with a reason ("Don't round buttons — reads consumer-tech, not engineered").
- [process] Keep a "Known Gaps" list: say what was not observed (forms, error states, mobile) so the agent doesn't invent it confidently.
- [process] Add an "Iteration Guide": build one component at a time; new variants are separate entries; ask whether the existing vocabulary can express a new component before adding tokens.
- [colour] Define colour by role groups: brand/accent, surface ladder, text levels, semantic.
- [colour] One accent, used scarcely, with an explicit list of the only places it may appear (CTA, focus ring, link, logo) — appears in nearly every file read.
- [colour] Name where the accent must NOT go (section backgrounds, card fills, decoration).
- [colour] Warm/action colour can be rationed to "means act here" only (Nintendo, Dell): colour carries meaning, not mood.
- [colour] Dark systems: build hierarchy with a 3–4 step surface ladder + hairlines instead of shadows (Linear, Bugatti).
- [type] Give each typeface one role and forbid crossovers (serif for narrative, sans for structure; mono for buttons/nav/captions) — "three faces, three roles".
- [type] Specify a full hierarchy table per role: size, weight, line-height, tracking, use.
- [type] Decide the emphasis device explicitly: weight OR size/tracking/case. Several premium systems ban bold entirely (Bugatti, WIRED display at 400).
- [type] State tracking direction per size: tight negative on large display sans (Linear -3px at 80px), wide positive on uppercase labels (2–6px).
- [type] Always list open-source substitutes for proprietary fonts and say what to preserve (the role split matters more than the exact face).
- [type] Reserve the biggest display style for one context only (Nike: 96px only in campaign heroes).
- [shape] Make the radius scale small and binary where possible (0 everywhere + pill for buttons only); intermediate radii "feel designed, not engineered".
- [shape] Document photo geometry (aspect ratios, corner treatment, crop direction on mobile) as part of the system.
- [space] Name a base unit (4 or 8px), a token scale, and a section rhythm; tie rhythm to content density (120px for photo-led luxury, 48–64px for dense retail/marketplace).
- [space] Write a "whitespace philosophy" sentence — whether density or air is the brand (Nintendo: packed is correct; Bugatti: compressing space breaks the brand).
- [layout] Describe the page's composition pattern in words (e.g. 1 large feature + 2-up + hairline-divided list; full-bleed tile alternating with 2-/4-up grid; never two campaign tiles side by side at the same scale).
- [components] Specify each component with its tokens and states (default, active/pressed, focus, disabled); variants are separate entries.
- [components] Limit the button vocabulary (e.g. "pill or icon-circular — that's the entire set"; one primary per viewport).
- [motion] Treat elevation as a table of levels with a stated ceiling (many systems: flat + hairline only; Airbnb: one shadow tier).
- [image] When photography is the identity, say so and move the chrome out of the way (Nike, Bugatti, Airbnb): "bigger photography before bigger type".
- [a11y] Responsive section must include touch targets (≥44px) and a collapsing strategy per component, not just breakpoints.
- [brand] A distinctive system usually comes from 1–2 strong, specific signatures (literal black page frame, beveled plates, transparent pill CTA, masthead band) applied consistently — not from many small effects.

## 4. AI tells / anti-patterns it bans
Recurring Don'ts across styles: atmospheric/decorative gradients; soft blurred drop shadows on cards; glassmorphism/"spotlight" cards; a second chromatic accent; accent used as section fill; uniformly rounded card systems with mid radii (8–12px everywhere); generic sans replacing a characterful display/serif; bold display weights by default; inline hex values; compressing whitespace to "fit more"; underlining non-links; two primary CTAs in one fold. WIRED explicitly praises refusing to look like a "SaaS marketing site". Note the files themselves also contain auto-generated filler (`ex-*` pricing/toast/modal blocks, TO_FILL) — that generic block is itself an AI tell to avoid copying.

## 7. Take / skip
Take:
- The DESIGN.md structure itself as Bexven's per-client output: Overview + Key Characteristics → token front matter → Colors by role → Type hierarchy table with role split → Layout/whitespace philosophy → Elevation levels → Shapes → named Components → Do/Don't → Responsive → Known Gaps. Generate one per client before building, so the Vercel static page and the later Elementor build (Global Colors/Fonts map cleanly to the tokens) share one source of truth.
- The habit of a stated governing idea + 1–2 signature moves per client — the best lever for making two funeral homes look different: different governing idea, different signature, different type-role split, different radius policy.
- Do/Don't written as hard limits with reasons; scarce-accent rule with an allowed-places list; no-bold or size/tracking emphasis as an option; open-source font substitutes.
- The Retro/Nintendo/Dell files as proof that a system can be dense, sharp, or loud and still coherent — useful counterweight to "everything airy and minimal".
Skip / handle with care:
- BRAND RISK: every file is a real company's identity (proprietary fonts, named colours like "Rausch", signature components like Bugatti's transparent pill). Do NOT hand a client a site "that looks like Stripe/Nike". Use the files only to learn structure and the kinds of decisions; never copy a combination of a brand's palette + type + signature component. Proprietary faces (Cereal, Futura ND, WiredDisplay, Bugatti fonts) are licensed and must not be used. Trade-dress/passing-off risk is real for client work, and it also defeats our goal (distinct sites).
- The auto-generated `ex-*` example blocks and TO_FILL markers (generic filler).
- The "never document hover" policy — fine for extraction accuracy, wrong for our own specs; we design states ourselves, hover included.
- The README's "copy a DESIGN.md and say build like this" workflow — produces derivative work.
- Brand-specific absolutes ("don't ship light mode", "true black canvas") — valid for that brand, not general rules.

## 8. Open questions
- preview.html / preview-dark.html are described in README but missing from the clone; not checked online.
- Values were extracted by tooling + screenshots; Known Gaps admit inferred values (e.g. Bugatti surfaces). Treat numbers as approximate.
- Conflicts with common "anti-AI" advice: real, well-designed brands here use purple/indigo (Linear, Stripe, Kraken, Mercury), cream canvas + serif (Notion, Oura, Mastercard, Starbucks, Claude terracotta), uppercase category eyebrows (WIRED, Sanity mono eyebrows), and dark-only marketing (Linear). So these are not bad in themselves — they become tells when used by default without a reason.
